১. এক নজরে
সিস্টেমটা কাজ করে, আর অনেক জায়গায় ভালো অভ্যাস আছে: প্রায় সব কুয়েরি prepared statement, বেশিরভাগ AJAX এ CSRF টোকেন, বিক্রির সময়ের দাম আলাদা করে সেভ রাখা। দুর্বলতা মূলত তিন জায়গায়:

টাকা ও স্টকের হিসাব এক জায়গা থেকে আসে না। একই কাজ (রিটার্ন অনুমোদন, দাম এডিট, ক্যাটাগরি এডিট) দুই-তিনটা পেজে আলাদা নিয়মে লেখা। ফলে এক পেজের মুনাফা আরেক পেজের সাথে মেলে না, আর কিছু কাজে স্টক ভুলভাবে বাড়ে-কমে।
কয়েকটা সরাসরি নিরাপত্তা ছিদ্র। স্টাফের লেখা নোট অ্যাডমিনের পেজে কোড হিসেবে চলতে পারে, অডিট লগ মোছার পাসওয়ার্ড কোডে লেখা, পুরনো সোর্স কোড আর কনফিগ ফাইল ব্রাউজার থেকে পড়া যায়।
প্রতিটা পেজ নিজের মতো। ২৪টা পেজের প্রত্যেকটায় নিজের সেশন-চেক, নিজের লগ ফাংশন, নিজের সাইডবার, নিজের SMS কোড। একটা নিয়ম বদলাতে ২৪ জায়গায় হাত দিতে হয়।

৮.৩ ReturnService
request(saleItemId, qty, note, userId): BEGIN → বিক্রির লাইন FOR UPDATE → আগে ফেরত (pending + approved) যোগ করে সর্বোচ্চ বের করা → qty ≤ সর্বোচ্চ → রিফান্ড = লাইনের দাম × qty, লাভ-কর্তন = লাইনের লাভ × qty → INSERT status pending (অনুমতি থাকলে সরাসরি approve() এর ধাপ) → COMMIT।
approve(returnId, adminId): BEGIN → রিটার্ন FOR UPDATE WHERE status='pending' → পণ্য FOR UPDATE → স্টক + qty → খাতায় return → স্ট্যাটাস approved, কে/কখন → অডিট → COMMIT।
reject(): শুধু স্ট্যাটাস, স্টক ছোঁবে না। ডিলিট নেই।
৮.৪ SupplierExchangeService
submit(): যাচাই → BEGIN → পুরনো পণ্য FOR UPDATE → নম্বর sequences থেকে → অনুমতি না থাকলে pending (payload JSON), থাকলে apply() → ছবি temp এ → COMMIT → ছবি সরান → নোটিফিকেশন কিউ।
apply() (একই ট্রানজেকশনে): ফেরত পিস খাতায় exchange_out (unit_cost = পুরনো কেনা দাম); নতুন পিস exchange_in। "একই পণ্য" হলে নতুন কেনা দাম = ওজনভিত্তিক গড়: (বাকি পিস × পুরনো দাম + নতুন পিস × নতুন দাম) ÷ মোট পিস।
cancel(): BEGIN → স্ট্যাটাস → এর সাথে যুক্ত (exchange_id) pending অ্যাডজাস্টমেন্ট বাতিল → COMMIT → pending ছবি মুছুন।
